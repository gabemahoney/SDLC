# Writing Apiary skills

Use this guide when writing or revising Apiary skills and their documentation. [The template](skill-template.md) supplies the shape; [the checklist](skill-review-checklist.md) checks the result.

## Keep what matters

- Start from today's skill and absorbed agent instructions, preserving proven guidance under the latest approved decisions and [product goals](goals.md), because older drafts may describe a superseded design.
- Keep workflow, ownership, outcomes and guards against likely harm, because capable agents need consequential rules rather than craft tutorials, rare edge cases or routine recovery instructions.
- State current requirements and confirmed limits, using judgement for qualitative needs, because rejected options, future work and invented precision become unintended scope.

## Write plainly

- Use short, complete sentences with clear subjects and concrete verbs, rewriting unclear paragraphs around their purpose, because shortening helps only while meaning survives.
- Give each rule its reason in the same sentence, so agents can apply it with judgement.
- Address the running agent as “you” and use Main Agent, Child Agent and established Glossary terms consistently, defining novel terms before use, so responsibilities and concepts stay clear.

## Give each rule one home

- State each rule once: skill-specific gates and transitions in the skill, shared workflow in workflow.md, craft in Guidance Documents, and configuration logic in templates or Protocol Files, because repeated versions drift.
- Reference those homes from the skill and respect the selected template's structure, so the skill remains executable with the Project's chosen configuration.

## Name the reading

- Use `setting:<name>`, `guide:<file>` and `protocol:<file>`, adding ` ## <Section>` inside the same backticks when needed, or full paths for fixed files, so references resolve consistently.
- Identify selected files through their selecting setting or resolved protocol reference, and read Guidance Documents from the main checkout, so agents use the intended configuration and established guidance.
- Justify each mandatory source for this skill and separate conditional reading, so each Run loads what its work needs.

## Make handoffs explicit

- Make Gates check the input ticket and necessary prerequisite states, with a response to failure, so work starts at the intended stage.
- Name outputs, locations, owned status changes and decision owners in Writes, defining ticket bodies in their writing skills, so each writer has an explicit contract.
- Make writing and reading instructions agree and derive checks from stated requirements, so handoffs introduce no hidden obligations.
- Use ticket IDs as inputs and keep findings, decisions, progress and handoffs on the affected tickets, so later agents have one durable record.
- Report ticket IDs, unresolved work with reasons and the next step in Done, so the caller can act.

## Delegate with ownership

- Delegate for independence, scale or parallel work, stating launch timing, expected result and whether each Child Agent is fresh or reused with scope and reason, so delegation has a purpose and a clear lifecycle.
- Assign distinct files to parallel writers and return revisions to the original planner, so work avoids conflicts and retains planning context.
- Give Main Agents responsibility for combined checks and executors responsibility for targeted checks, so validation has an owner at each level.

## Review with judgement

- Review against the main brief, approved intent, Guidance Documents and actual files, because a child document or reviewer finding alone can misrepresent the work.
- Define findings as blocker (wrong), suggestion (fragile or confusing) or nit (style), so the Main Agent can weigh their consequences.
- Have the Main Agent fix accepted findings, record reasons for declining minor findings and refer product decisions or requirements conflicts to the Managing Intelligence with a recommendation, because decision authority must remain clear.
- Read the revision cold for clarity and consistency, compare it with the previous version and use the checklist, trimming after each round, so edits preserve useful meaning without accumulating repetition.
- Stop when findings are trivial or further cuts would lose information, because reviews can always produce another wording change.
